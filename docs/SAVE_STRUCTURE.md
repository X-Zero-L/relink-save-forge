# 存档装备关联结构

本文记录由实机存档与游戏 UI 交叉验证的最小安全不变量。字段编号沿用现有社区/编辑器 catalog。

## 命运篇章与任务向量

Relink 2.0 的命运篇章使用同 unit 配对的 `3501/3502`：

- `3501`：命运篇章 Key 的 GBFR 自定义 XXHash32；
- `3502`：该 Key 的状态，已确认完成值必须精确为 `30`；
- 两个字段各有 820 条记录，但数据库只有 319 条 `FATE_*` 与 5 条 `REMI_*`，余下 496 条是固定空占位；
- 空占位为 `3501=887AE0B0`、`3502=5`，不得重新分配或改写；
- 5 条 `REMI_*` 必须保留，只有 319 条 `FATE_*` 对应的 `3502` 可以进入完成集合。

数据库行序与存档 unit 顺序不同。正确实现必须对每个文本 Key 计算哈希，在 `3501` 中要求唯一匹配，再修改同 unit 的 `3502`；缺失、重复、冲突或数量不符时应在写盘前失败。

命运战斗任务使用长度为 100 的 `2560/2561` 向量：

- `2560` 保存任务 ID，56 个非零位置与 44 个空位置必须完全保留；
- `2561` 保存通关计数，只能让 56 个有效位置满足 `max(old, 1)`；
- 数据库中有 58 条非零 `MissionQuestId` 引用，但只有 56 个唯一任务，因此不能按篇章数量直接推算向量索引；
- 44 个空位置的 `2561` 必须继续为 `0`，已有大于 `1` 的计数不得降低。

完成全部 319 条真实 Fate 会满足所有角色最后两个因子槽的数据库条件，不需要新造 `1403` 槽位开关。`5801/5815` 只观察到统计、通知、成就等副作用，当前没有完整索引映射；它们不是 Fate、槽位或 StatusUP 的独立主状态，必须保留，禁止全量设值或把一次探针索引复制到其他角色。

命运完成流程必须保证 `3501`、`2560` 与主线字段 `2510/2511/2520/2522` 的摘要逐项不变。完整数据库与实机差分契约见 [FATE_EPISODES_2_0.md](FATE_EPISODES_2_0.md)。

## 角色与因子槽

29 名可玩角色已经有预分配记录。角色可用状态的最小安全写法不是覆盖整行，而是只对同一角色 unit 的 `1305` 执行自然激活 mask 的按位 OR：

- `PL0000`、`PL0100`、`PL0200`、`PL0300`、`PL0400`、`PL0500`、`PL0600`：OR `0x01`；
- `PL1900`：OR `0x09`；
- 其余清单确认的可玩角色：OR `0x11`。

现有 `1305` bit 必须全部保留。角色解锁流程不能写 `1302/1315` 的猜测值，也不能顺带覆盖等级、EXP、MSP、装备、命运篇章或主线字段；第二次执行必须没有记录变化。

角色记录的 `1403[0..11]` 表示 12 个因子槽。每个已装备槽必须同时满足：

1. 角色 `1403[slot]` 与目标 Gem 记录的 `2702` 实例标识对应；
2. 目标 Gem 的 `2706` owner 是该角色的角色 GBID 哈希；
3. 角色侧槽引用与 Gem owner 双向一致，不得只改单边；
4. Gem `2703` 是因子 GBID 哈希，`2704` 是因子等级，但这两个字段本身不足以构成有效装备关系。

空槽、未装备库存和已装备实例必须分别处理。复制一个 `2703` 值而不建立 `1403 ↔ 2702/2706` 关系，只会产生库存外壳或损坏引用。

## 因子内部 trait lanes

每个 Gem unit 的内部词条 lane 使用以下 unit 映射：

```text
traitUnit = 120000000 + (gemUnit - 30000) * 100 + slot
```

其中 `slot` 是该因子的内部 trait lane 序号。lane 使用：

- `1701`：trait/skill ID 哈希；
- `1702`：对应 lane 的等级/状态值。

双词条因子不能只改 `2703` 的显示外壳。主词条与第二词条的 `1701/1702` lane 必须和目标因子、等级及数据库组合一致。

## 角色与当前武器

角色当前装备字段与武器实例必须满足：

1. 角色 `1402` 指向目标 Weapon 记录的 `2802` 实例标识；
2. Weapon `2802` 必须是有效、非零、唯一的实例标识；
3. Weapon `2803` 才是武器 GBID 哈希；
4. `1402 ↔ 2802` 必须双向可解析，不能只写 `2803`；
5. 强化、觉醒和其他武器字段应附着在同一个有效实例上。

## 正式武器创建与补齐

Relink 2.0.2 为物理武器预分配 256 个 unit（`40000..40255`）。公共创建器只把同时满足以下完整模板的 unit 视为规范空槽：

```text
2802=[0]
2803=[887AE0B0]
2804=[0]
2805=[0]
2806=[0]
2807=[0]
2813=[0]
2814=[887AE0B0]
2815=[0]
2816=[887AE0B0]
2817=[0]
2818=[887AE0B0,887AE0B0,887AE0B0,887AE0B0,887AE0B0]
```

只要 `2802`、`2803` 或其他模板字段形成半空壳，就不能擅自修补或复用该 unit。创建器的目标集合固定为数据库确认的 174 把正式武器：

- 160 把有完整 2.0 终盘运行时身份与五项技能向量，写入满经验 `162540`、突破 `6`、加值 `99` 和超限等级 `7`；
- 14 把没有完整终盘运行时规格，只保持正式基础身份，`2817=0` 且 `2818` 为空向量；
- 新 `2802` 实例 ID 从当前 `2801` 计数器后连续分配，计数器不得低于任何已占用实例 ID。

未知或模组武器只要是结构完整的已占用实例，就必须逐字段保留。若发现重复非零 `2802`、同一正式武器存在多个实例、`2801` 低于当前最大实例 ID、非规范半空壳、规范空槽不足或保存版本不匹配，转换必须在写盘前失败。已有正式武器可以规范化/强化，但不能通过删除未知实例来腾位置。

## 当前武器的 Wrightstone/祝福快照

武器祝福不是通过库存 `210x` Wrightstone 实例链接到武器：

- 武器 `2816` 只保存 Wrightstone 的 `ITEM_*` 外壳哈希，不是库存实例 ID；
- 真正生效的三条内部词条保存在武器自己的 `130m` 运行时 lane；
- 对物理 Weapon unit `U`，第 `lane` 条（0–2）的位置是：

```text
traitUnit = 130000000 + (U - 40000) * 100 + lane
```

每条 lane 仍使用 `1701` 保存技能哈希、`1702` 保存等级。定位 `U` 时必须先由角色 `1402` 找到相同 `2802` 的物理武器记录；把 `2802` 槽号直接代入公式会写到错误武器。完整赋值必须同步修改该武器的 `2816` 和三组 `130m/1701/1702`，只改外壳仍会产生“显示正确、内部旧值”的坏记录。

库存 Wrightstone 使用 `210x` 与 `140m`，和武器快照没有指针关系。默认配装流程不得修改 `210x/140m`，也不得宣称某个库存石已绑定到武器。已验证运行时等级上限为 99；大于 99 会被游戏视为无效。

## 已装备召唤石

召唤石是全队共享的四槽系统：

- `1451`：四个已装备召唤实例 ID；
- `1452`：300 项召唤类型目录；
- `1453`：与目录位置对应的解锁标志；
- `1454`：召唤实例 ID 计数器；
- `1455`：召唤管理器初始化状态；
- `1456`：实例 ID，用于解析 `1451`；
- `1457`：召唤石外壳/类型哈希；
- `1458[0]`：一个通用技能被动，`1459[0]` 是对应等级；
- `1458[1]`：一个召唤基础/上限加成，`1459[1]` 是对应等级；
- `1460`：尚未完全解码的状态字段，不能按数据库稀有度推导或重写。

第二槽不是任意因子槽。两类 pack 的边界不同：

- **Existing-only 重配**：只允许按 2.0.2 `summon_lot/summon_curve` 白名单修改现有四颗目标的 `1458/1459` 索引 0；`1451/1456/1457/1460` 以及索引 1 的加成哈希和等级必须逐项保留。
- **Create + Equip**：可以在 1000 个预分配实例中使用规范空槽，分配新的 `1456`、同步 `1454`、在 `1452` 中按类型哈希唯一查找位置并把对应 `1453` 设为 `1`，最后更新 `1451`。不得硬编码目录索引。

召唤实例的规范空槽为：

```text
1456=[0]
1457=[887AE0B0]
1458=[887AE0B0,887AE0B0]
1459=[-1,-1]
1460=[0]
```

创建包的四个目标元组来自数据库白名单和实机保存验证：Rolan、Lilith、Beelzebub、Lucilius 的第一被动等级均为 `15`，第二基础加成等级均为 `9`，`1460` 均写为游戏保存后规范化的值 `6`。`1460` 的具体语义仍未解码；值 `6` 不是按稀有度推导的通用规则，也不得应用到其他召唤石。创建包会规范化它所选中的四个目标实例，existing-only 包则必须保留原值。

Relink 2.0 觉醒/超限字段已经进一步确认：

- `2807`：旧觉醒等级；旧觉醒武器为 `10`，普通武器为 `0`；
- `2815`：状态 bit flags，必须保留已有 bit；
- `2817`：2.0 超限等级，完成值 `7`，不是布尔值；
- `2818`：五项武器技能哈希向量，每槽由该武器的 `WeaponSkillLevelRebuildId1..5` 独立解析。

`2818` 的正确关系是：第 N 槽读取 `WeaponSkillLevelRebuildIdN`，在 `weapon_skill_level_rebuild` 中查找 `Unk13` 等于该曲线 ID 的行，并写入所选行 `Unk12` 的哈希。若武器行有对应 `WeaponSkillId`，优先选择同技能哈希；否则按数据库稳定顺序选择第一/唯一行。不同武器的第五槽可以不同，不能套用统一最终技能。

实机保存证明覆盖 74 个满级实例、370 个技能槽，全部与数据库逐槽解析结果一致。当前存档共识别 171 个可超限实例、159 种规格；其中普通武器的 `2807` 必须继续为 `0`。

完整数据库曲线、运行时哈希和实机证明见 [WEAPON_REBUILD_2_0.md](WEAPON_REBUILD_2_0.md)。

因此以下写法被明确禁止：

- 在空记录只设置 `2803`，而让 `2802 = 0`；
- 角色 `1402` 指向不存在或重复的 `2802`；
- 通过连续编号猜测武器 GBID，然后直接写入存档；
- 把觉醒阶段数据库行误当成独立收集武器实例。
- 把旧觉醒 58 种武器误当成全部可超限武器；
- 用 `_10` 后缀合成技能，或给所有武器写同一个第五技能。

## 已确认的非连续武器编号

数据库中以下角色没有 `_05`，第六把正式武器为 `_07`：

- `PL2100`
- `PL2200`
- `PL2300`

生成清单时可以生成候选哈希用于数据库反查，但只有匹配到真实基础武器行的 ID 才能发布或写入。

## 暗龙身份修正

游戏内 UI 与当前格式存档共同确认：

- Fediel / 暗龙：`PL2900`
- 角色专属因子家族：`GEEN_178_*`

旧映射 `PL2800 / GEEN_177_*` 不得继续用于暗龙预设。
