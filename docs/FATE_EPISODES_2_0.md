# Relink 2.0 命运篇章与因子槽契约

本文记录 Relink 2.0 `fate_episode` 数据库、存档结构和实机前后差分共同确认的命运篇章模型。完成脚本必须以数据库 Key 的 GBFR 哈希定位存档记录，不能依赖数据库行号、存档 unit 顺序或连续编号猜测。

## 数据源与完整范围

权威 catalog 为 `catalogs/fate-episodes-2.0.json`，由 `scripts/generate_fate_episode_catalog.py` 从 Relink 2.0 `fate_episode.tbl` 生成。

- 原始 `fate_episode.tbl` SHA256：`9B6AAF0748A19B5C51FE298F5C062DDEB987EA158423BF116A7E2B4201AA5EF6`
- catalog 源 SQLite SHA256：`350AFCE0FB0A0C784EA3F4EF05B19426F6BA4CBCAFDCC5C18B765AC878B70143`
- 数据库总行数：324
- 真实命运篇章：319 条 `FATE_*`
- 辅助记录：5 条 `REMI_*`
- 角色数：29
- 每名角色：`_00.._10` 共 11 篇

存档中的 `3501/3502` 各有 820 个 unit：

| 类型 | 数量 | 处理规则 |
| --- | ---: | --- |
| `FATE_*` | 319 | 完成时把配对的 `3502` 精确写为 `30` |
| `REMI_*` | 5 | 完全保留 |
| 空占位 | 496 | 完全保留；`3501=887AE0B0`、`3502=5` |

数据库顺序与存档 unit 顺序不一致。已知只有少量行偶然同位，因此禁止按行号或数组位置直接映射。

## `3501/3502` 配对规则

每条数据库记录的文本 `Key` 使用 `scripts/gbfr_hash.py` 中的 GBFR 自定义 XXHash32 算法转换为 32 位哈希：

```text
fate_hash = gbfr_hash(database_row.Key)
```

然后在 `3501` 中查找该哈希，并使用相同 unit 的 `3502` 作为状态。发布脚本必须要求：

1. 319 个 `FATE_*` 哈希全部存在；
2. 每个哈希只匹配一个 `3501` unit；
3. 5 个 `REMI_*` 与 496 个空占位不进入完成集合；
4. 缺失、重复、哈希冲突或数量不符时在写盘前失败。

实机状态语义已经确认：

| `3502` 值 | 已确认含义 |
| ---: | --- |
| `30` | 篇章完成 |
| `21` | 下一篇已解锁但尚未完成 |
| `5` | 未解锁状态；也是空占位的固定状态 |

其他既有状态值应由完成脚本直接覆盖为 `30`，不能使用 `max(old, 1)`，也不能把完成值误写成 `1`。

## 战斗任务 `2560/2561`

`fate_episode` 中有 58 条非零 `MissionQuestId` 引用，对应 56 个唯一任务 ID。`PL0000` 与 `PL0100` 共享两项任务，因此数据库引用数大于唯一任务数。

存档任务向量长度为 100：

- `2560`：任务 ID，56 个非零位置、44 个空位置；必须完全保留；
- `2561`：任务通关计数；56 个有效位置只需保证 `max(old, 1)`；
- 已有更高计数必须保留，例如实机探针中的 `2`；
- 后 44 个空位置必须继续为 `0`。

完成 Fate 时只能通过数据库 `MissionQuestId` 在 `2560` 中反查位置，禁止按角色序号或篇章后缀推算向量索引。

## 最后两个因子槽

实机探针确认，角色最后两个因子槽由指定 Fate 完成状态开放，没有观察到独立的角色槽位开关。

通常负责两个槽位的是：

```text
FATE_<角色>_04
FATE_<角色>_08
```

Relink 2.0 数据库中的特殊角色为：

| 角色 | 第一个槽位篇章 | 第二个槽位篇章 |
| --- | --- | --- |
| `PL2800` | `_06` | `_10` |
| `PL2900` | `_00` | `_10` |

`PL2500` 的实机探针同时验证了普通规则：

- `_04` 的 `MissionQuestId=00300025` 位于 `2560[54]`；完成时 `3502` unit 268 从 `20→30`，下一篇 unit 269 从 `5→21`，`2561[54]` 从 `1→2`；游戏确认开放一个因子槽。
- `_08` 的 `MissionQuestId=00301025` 位于 `2560[48]`；后续保存中 `2561[48]` 从 `1→2`；游戏确认开放另一个因子槽。

因此，全量完成 319 条真实 Fate 会覆盖普通角色与两个特殊角色的全部槽位条件，不需要发明额外的 `1403` 槽位标志。

## `PL2500_10` StatusUP 实机探针

用户在完成第二槽相关篇章后，又单独完成并保存了 `FATE_PL2500_10` 的战力提升篇章。两个连续保存点提供了干净差分：

| 保存点 | SHA256 | `FATE_PL2500_10` |
| --- | --- | ---: |
| `SaveData1_BackUp.dat`，2026-07-20 19:59:10 | `0196D8CEF2A71843D830D1A75B43357CEF94892056533164F18C06F6E59871AE` | `21` |
| `SaveData1_BackUp2.dat`，2026-07-20 19:59:20 | `D7E8078BC099D5D2CAC147A3B6D4912F246F81B1190E17DF750A2513FD29D24A` | `30` |

该次完成没有修改角色 `13xx` 基础属性或成长记录。除 `3502` 外，只出现系统统计/通知类副作用：

- `5801[786]`: `false→true`
- `5815[593]`: `10→11`
- `5815[996]`: `0→6`
- `5815[1036]`: `5→6`
- `5815[1066]`: `0→1`

其中 `5815[593]` 会随 `PL2500` 已完成 Fate 数量逐篇递增：`4→5→10→11`。这证明它是完成统计，而不是槽位或 StatusUP 的独立主状态。

完整文件字节审计也没有发现解析器之外的 gameplay 开关：

- 第二槽阶段的 675 个变更字节中，671 个落在已解析标量或活动哈希表；其余 4 个仅属于 wrapper 校验区；
- `_10` StatusUP 阶段的 90 个变更字节中，86 个落在已解析标量或活动哈希表；其余 4 个同样仅属于 wrapper 校验区。

结论是：Fate 完成状态负责槽位与篇章奖励条件；没有证据支持另写一个独立角色开关。

## 禁止批量伪造 `5801/5815`

`5801` 与 `5815` 还会随战斗、统计、通知、成就和其他游戏行为变化。当前没有完整数据库能够把它们的每个数组索引安全映射到具体含义。

完成脚本必须保留这两个字段，不得执行以下操作：

- 把 `5801` 全部设为 `true`；
- 把 `5815` 全部设为统一最大值；
- 把一次 `PL2500` 探针的索引复制到其他角色；
- 为了模拟奖励弹窗而猜测未知计数。

若未来需要补全标题、统计或通知状态，必须先建立独立的数据库映射和实机差分证明，不能把它混入 Fate 完成逻辑。

## 主线与结构保护

命运篇章完成流程必须保证以下字段摘要逐项不变：

```text
2510
2511
2520
2522
```

实机探针从第一个槽位保存点到最终 StatusUP 保存点期间，上述四个主线字段、全部 820 条 `3501` 和完整 `2560` 均完全一致。

安全实现只允许修改：

```text
3502  # 仅 319 条 FATE_* 对应 unit，精确写 30
2561  # 仅 56 个有效 MissionQuestId 位置，保证至少 1
```

同时必须保留 SteamID、payload 大小、记录数、REMI 状态、空占位状态和所有已有更高任务计数。

## 发布前验证

完成脚本及一键流水线必须证明：

- 319/319 条 `FATE_*` 状态精确为 `30`；
- 5 条 `REMI_*` 与 496 个空占位零变化；
- 56 个有效 `2561` 位置均不小于 `1`，44 个空位置仍为 `0`；
- `3501` 与 `2560` 零变化；
- 主线字段 `2510/2511/2520/2522` 零变化；
- 记录无新增、删除或重排；
- 活动存档哈希有效，SteamID 和文件结构不变；
- 对输出再次运行时逻辑变化为零；
- 脚本不直接覆盖游戏正在使用的活动存档目录。
