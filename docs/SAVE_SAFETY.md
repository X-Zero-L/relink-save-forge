# 存档、SteamID 与哈希安全

## 不可省略的步骤

- 游戏必须完全退出。
- 先备份 `SaveData1.dat`、`SaveData1_BackUp.dat`、`SaveData1_BackUp2.dat`（存在几个就备份几个）。
- 备份目录应与活动存档目录分开，并保留 SHA-256 清单。
- Steam 云冲突时先辨认时间、大小和哈希，不要盲目覆盖。
- 永远在副本上验证，再替换活动文件。
- `run_full_rebuild.py` 的输入、工作目录、最终候选和报告都应位于活动目录之外；流水线会拒绝写入 `%LOCALAPPDATA%\GBFR\Saved\SaveGames`。
- 候选通过活动哈希、主线摘要、记录结构和数据库清单审计后，才由用户手动替换活动文件；工具不会自动部署候选。

## SteamID64 头部

PC 存档头部偏移 `0x04` 起的 8 字节是小端 SteamID64。`resign_steamid.py` 的安全约束：

- 要求同时传入 `--expected-old-steam-id` 和 `--new-steam-id`；
- 文件中的旧值不匹配就终止；
- 默认 dry-run；
- `--apply` 时自动备份并使用同目录临时文件原子替换；
- 写入后重新读取验证。

该操作只处理账号头部绑定。它不会修复被错误修改的 FlatBuffer/payload，也不会重新计算内部存档哈希。

## ID 哈希与存档完整性哈希不是一回事

### GBID 字符串哈希

角色、武器、因子和技能 ID 使用 GBFR 自定义 XXHash32 变体。实现见 `scripts/gbfr_hash.py`。它用于把 `PL2800`、`WEP_PL2800_06`、`GEEN_177_93` 等文本 ID 转成 32 位值。

### 存档 payload 哈希

游戏存档使用种子 `0x2F1A43EBCD` 的 XXHash64，并维护十个候选段。字段 `SAVEDATA_HASHSEED`（uint id `1003`）决定活动槽：`active_index = hash_seed % 10`。

游戏正常写出的样本通常只有活动槽与当前 payload 匹配。安全编辑器应只刷新活动槽。批量刷新十个槽虽然“看起来都通过”，但会偏离游戏正常写盘形态。

候选段参数（`start`, `sub_size`）为：

```text
(0x58,0x80) (0x30,0xA0) (0x28,0x30) (0x38,0xC0) (0x40,0xB0)
(0x68,0x50) (0x48,0x60) (0x70,0x90) (0x50,0x40) (0x60,0x70)
```

完整计算还依赖正确解析存档容器边界和 payload size；不要仅凭固定偏移对未知版本存档写哈希。

## 主线保护

配装和物品工具不应通过“全字段设满”实现。若目标是不推进主线，必须把任务、章节、剧情标志视为禁止写入区，并在写前/写后做字段级 diff。当前完整重建流水线把以下字段作为硬保护摘要：

```text
2510
2511
2520
2522
```

最终候选与 `--baseline` 的四项摘要不一致时，验证必须失败。`--baseline` 应是与输入对应的已知正常离线副本，而不是流程生成的中间文件。

## 命运篇章边界

命运篇章完成不是全局统计字段填满操作。安全流程只允许：

- 把 319 条数据库确认的 `FATE_*` 配对 `3502` 精确写为 `30`；
- 把 `2560` 中 56 个有效任务位置的 `2561` 提升到至少 `1`，并保留已有更高值。

以下内容必须零变化：

- 5 条 `REMI_*` 与 496 条固定空占位；
- 全部 `3501` Key 与完整 `2560` 任务 ID 向量；
- `2561` 的 44 个空位置；
- 主线字段 `2510/2511/2520/2522`；
- 未完整映射的 `5801/5815` 统计、通知与成就向量。

不得把 `5801` 全部设为 `true`、把 `5815` 统一写成猜测最大值，或把某个角色一次实机探针出现的数组索引复制到其他角色。它们不是最后两个因子槽或 StatusUP 的独立开关。详见 [FATE_EPISODES_2_0.md](FATE_EPISODES_2_0.md)。

## 离线流水线与部署边界

`scripts/run_full_rebuild.py` 只生成候选：它拒绝原地覆盖输入、拒绝覆盖已有产物，并拒绝把工作目录、候选存档、审计或报告写入活动 GBFR 存档目录。推荐流程是：

1. 关闭游戏并把最新活动存档复制到独立目录；
2. 对副本运行一键流水线，保留各阶段 `.dat` 与 JSON 审计；
3. 核对最终报告中的活动哈希、SteamID、主线摘要、319/5/496 Fate 数量、56/44 任务数量和结构不变量；
4. 保留原活动文件及 SHA-256 后，再手动部署最终候选；
5. 进游戏检查命运篇章、12 个因子槽、武器切换和保存退出，再决定是否恢复云同步。

## 关联完整性

装备写入不是只替换一个哈希。角色、因子、trait lane 和武器实例之间存在双向关联；任何修改都必须保持 [SAVE_STRUCTURE.md](SAVE_STRUCTURE.md) 中的关系。

- 禁止只写 `Weapon 2803` 制造“有武器 ID、无实例 ID”的外壳。
- 禁止保留 `Weapon 2802 = 0` 却让角色 `1402` 指向该记录。
- 禁止按 `_01`、`_02`、`_03` 的连续编号猜测未在数据库确认的武器。
- 因子装备必须同时核对角色 `1403[0..11]`、Gem `2702`、Gem `2706` 和对应 trait lanes。
